# 작업 과정과 선택 이유 정리

작업자가 결과물을 자신의 말로 설명할 수 있도록, **실제로 확인된 작업 과정**을 짧은 복습 문서로 유지한다. 대상은 코드뿐 아니라 데이터 분석·문서·업무 자동화 결과물도 포함한다.

## 결과 파일

- 과제 루트에서 **최신 제출 안내 → README → 제공 템플릿**을 대조해 필수 문서의 정확한 경로·파일명·대소문자·필수 항목을 확인한다. 사용자가 기억하는 이름은 파일을 찾는 단서로 사용한다. 안내가 충돌하면 충돌한 부분을 표시하고 확인한다.
- 지정 문서가 있으면 요구된 경로와 양식에 내용을 직접 작성한다. 기존 제목·필수 필드·사용자가 쓴 메모를 보존한다. 사용 설명서는 다음 사용자가 재현할 내용, AI 협업 기록은 작업자가 어떤 판단을 거쳤는지에 필요한 근거를 담는다.
- 지정 문서가 없으면 **실제 과제 폴더의 `WORK_REVIEW.md` 한 파일**을 기본으로 삼고 [복습 양식](assets/WORK_REVIEW.md)을 참고한다. 지정 문서와 별도의 복습본도 요청받았으면 파일 규정이 허용하는 위치에서 기존 기록을 연결한다. 제출 파일이 한정되면 자기 점검은 제출 전 허용된 대화에서 진행한다.
- 공개 자료를 내려받은 참고 저장소에 작업 내용을 작성하지 않는다. 문서에는 필요한 상대 파일 경로·함수·기록 위치를 연결하고, 민감한 원문·키·개인 식별 정보는 복사하지 않는다. 생성 문서를 외부로 전송하거나 push하지 않는다.
- 기존 사용자의 설명과 메모를 보존한다. 중복을 합치고 오래된 상태를 고치되, 변경 이유나 미해결 사항을 지워서 작업을 성공한 것처럼 보이게 하지 않는다.

## 언제 갱신할지

요구사항 확인, 중요한 설계 선택, 원인 확인과 수정, 검증 결과 변경처럼 **의미 있는 작업 단위가 끝날 때** 관련 부분만 갱신한다. 모든 명령마다 전체 문서를 다시 쓰지 않는다. 제출 전에는 실제 최종 파일 및 최신 검증 기록과 대조해 상단 요약을 정리한다.

요청이 정리 작업에 한정되면 구현·재설계·추가 테스트를 자동으로 시작하지 않는다. 필요한 근거를 찾지 못한 항목은 미확인으로 남긴다.

## 지정 문서에 담을 내용

| 문서의 역할 | 무엇을 기록할지 |
|---|---|
| 실행·사용 안내 | 전제 조건, 작업 위치, 실제 진입 명령 또는 파일, 사용자 역할별 첫 동작, 대표 입력과 기대 결과, 결과 확인 위치를 연결한다. 확인한 복구 절차가 있으면 사용자에게 보이는 증상 옆에 적는다. 코드에서 찾은 절차와 실제로 끝까지 실행한 절차의 확인 범위를 밝힌다. |
| AI 협업·개발 기록 | 중요한 작업마다 요청한 목표, AI가 제안·작성한 내용, 본인이 채택·수정·기각한 내용과 이유, 관찰된 결과와 근거 파일을 연결한다. 담당자 답변으로 바뀐 기준, 실패한 시도, 미확인 결정도 해당 항목에 남긴다. |

**오류 하나의 기록**은 재현 조건(역할·입력·직전 행동)과 기대 동작, 실제 증상, 원인을 좁힌 근거, 수정 위치와 이유, 같은 사례의 재검증, 남은 영향을 순서대로 적는다. 원인 후보를 기각했다면 어떤 관찰 때문인지, 실제 검증이 일부라면 마지막으로 확인한 단계가 어디인지 적는다.

예를 들어 로그인 제출 후 다음 화면으로 이동하지 않는 증상은 **인증 응답 → 세션 유지 → 대상 경로와 권한 → 화면 표시** 중 어디까지 확인했는지로 좁힌다. 성공 응답만 관찰했다면 그 사실과 이후 단계의 확인 상태를 적는다. 변경 후 단위 테스트만 통과했다면 단위 테스트 결과와 실제 사용자 화면 재검증 상태를 나눠 적는다. 원인·수정·재검증을 관찰한 기록이 생길 때 해당 항목을 갱신한다.

## 근거 수집과 작성

1. 과제 README, 제공 파일, 실제 변경 파일, 담당자 답변과 대화 기록, 기존 계획·결정·진행·검증 기록 중 관련 부분을 읽는다. 파일명 자체를 가정하지 말고 존재하는 자료를 사용한다.
2. **목표 → 입력 → 처리 → 결과 → 확인 방법**을 비전문가도 이해할 말로 연결한다. 구성요소가 실제로 어떻게 이어지는지 파일·함수나 산출물 위치를 덧붙인다. 화면이 필요 없는 결과물에 웹사이트 구조를 강요하지 않는다.
3. 중요한 선택마다 실제 요구사항·제약, 채택한 방법, 검토한 대안, 얻은 점과 감수한 점을 기록한다. 당시 선택 이유가 기록에 없으면 `선택 이유 미확인`으로 표시한다. 사후에 떠올린 대안을 당시 검토한 것처럼 쓰지 않는다.
4. 문제는 **관찰된 증상 → 원인 확인 근거 → 조치 → 같은 사례의 재검증**으로 정리한다. 원인이 아직 가설이면 명시하고, 해결 여부도 분리한다. 기록에 없는 장애나 시행착오는 만들지 않는다.
5. 검증은 입력·명령 또는 확인 절차·관찰 결과·근거 위치를 남긴다. `계획`, `미실행`, `실행 실패`, `통과`, `미확인`을 구분한다. 로그가 없으면 통과로 쓰지 않는다. 이전 성공 이후 파일이 변경됐다면 최종 상태 검증 여부를 별도로 표시한다.
6. AI가 제안·작성한 부분과 사용자가 확인·결정·수정한 부분을 근거대로 구분한다. 사용자의 확인 기록이 없으면 `본인 확인 필요`로 남기고, 확인되지 않은 1인칭 경험이나 이해를 대신 서술하지 않는다.
7. 개선 수치를 쓸 때 지표 정의·기준안·비교 기간이나 사례·함께 달라진 비용 또는 자원을 기록한다. 측정한 효과와 추정을 구분하고, 남은 한계와 다음 개선을 적는다.

핵심 결정과 문제를 우선해 읽을 분량을 줄인다. 긴 로그와 코드 전체는 붙이지 않고 근거 위치와 짧은 결과만 남긴다. 앞부분은 빠르게 복습할 수 있게, 뒷부분은 설명의 근거를 찾을 수 있게 작성한다.

## 이해도 점검

제출 전에 **작성한 문서의 주장과 실제 산출물·변경·검증 기록**에서 중요한 사례를 골라 자기 점검 질문을 만든다. 사용자가 복습 문항 수를 지정하면 그에 맞추고, 기본은 근거가 있는 범위에서 최대 6개로 추린다. 질문마다 실제 결정·증상·측정값 중 하나와 다시 볼 근거 위치를 붙인다. 예를 들어 “어떤 관찰로 원인 후보를 좁혔나?”, “마지막 테스트는 어느 단계까지 확인했나?”, “개선 수치를 비교할 때 자원 조건도 같았나?”를 이번 작업에 맞게 구체화한다. 답할 근거가 없으면 `본인 확인 필요`로 표시한다. 복습 질문은 허용된 복습본 또는 제출 전 대화에 둔다.

실제 작업과 맞지 않는 질문의 전제가 발견되면 차이를 분명히 기록한다. 작업 내용을 질문에 맞춰 꾸미지 않는다.

## 제한된 평가 환경에서 사용

AI 사용이 허용된 작업 단계에서, **제출 전 복습과 작업 기록** 용도로만 적용한다. AI 금지 단계에서는 문서를 생성·갱신하거나 문항에 답변하지 않는다. 그 단계에서 기존 문서를 열람할 수 있다고 가정하지 않으며, 해당 환경의 안내를 따른다. 직접 작성해야 하는 평가 답안의 자동 입력·복사·붙여넣기나 차단 우회 기능은 제공하지 않는다.
