# 시간 제한 실무 과제 진행표

[README](../README.md) · [스킬 목록](CATALOG.md) · [모델 선택](MODELS.md) · [자세한 문제 해결 순서](WORKFLOW.md)

결과물 형식을 미리 정하지 않고 README와 업무 담당자 답변으로 확정하는 순서입니다. 특정 평가의 공식 안내가 아니며, 실제 시간·도구·자료·제출 규정을 우선합니다.

## 1. 제공 환경과 과제 폴더 확인

- 최신 안내, 남은 시간, 필수 결과물, 제출 경로와 확정 절차를 먼저 확인합니다.
- 터미널에서 `pwd`, `ls`로 현재 위치와 파일을 확인합니다. README와 제공 파일이 있는 실제 과제 폴더에서 시작합니다. 경로를 추측하거나 참고 레포에서 구현하지 않습니다.
- 제공 Codex를 사용하는 환경이라면 `codex`로 실행하고 `/status`, `/model`에서 상태와 모델을 확인합니다. 실제 제공 명령과 선택지를 따르며, 버전 고정 환경에서 업데이트·재설치를 하지 않습니다.
- 시작 설정 제안은 **Sol 6.1 / medium / Fast OFF**입니다. 필수 규칙이 아니며 실제 지원 여부를 확인합니다. 지정된 작은 수정은 low, 어려운 원인 분석은 필요할 때 high를 검토합니다. Fast의 사용량 차감과 과제의 평가 산식은 같다고 가정하지 않습니다.

시간 배분은 **읽기·질문 → 작은 완성본 → 필수 기능 보완 → 검증·수정 → 복습·제출**로 잡습니다. 제출 준비 시간까지 포함하고, 마지막 순간까지 구현을 이어가지 않습니다.

## 2. 처음 보낼 요청

아래 요청을 현재 과제 폴더에서 실행 중인 Codex에 보냅니다. 외부 자료의 복사·붙여넣기나 파일 반입이 제한된 환경에서는 허용된 입력 방법을 따릅니다.

```text
현재 과제의 README·제공 파일 목록·실행 및 제출 안내를 먼저 읽어줘.
https://github.com/parkhyunjae01/ai-work-skills 를 별도 참고 폴더에 내려받고,
docs/TIMED_WORK.md와 catalog.json에서 필요한 스킬만 골라줘.

결과물을 웹사이트로 가정하지 말고 요구된 형식과 제공 환경에 맞춰 판단해줘.
업무용 스킬 1~2개와 skills/work-review/SKILL.md를 읽어 적용하고,
기존 구조·라이브러리를 우선 사용해줘. 일괄 설치나 별도 MCP 연결로 시작하지 마.
스킬은 bundled·authored 항목의 local_path를 우선 읽어줘.
맞는 스킬이 없으면 추가 탐색에 매달리지 말고 제공 환경으로 진행해줘.

먼저 다음만 짧게 정리해줘.
1. 해결할 업무 문제, 입력, 필수 결과물, 제약, 완료·제출 기준
2. README만으로 확정된 내용과 미확인 사항
3. 업무 담당자에게 먼저 물을 질문 최대 3개와 각 답변이 바꾸는 구현 결정
4. 실제 입력 하나를 끝까지 처리하는 최소 구현과 남은 시간 배분

지금은 분석·질문·계획까지 진행해줘. 확인이 필요한 업무 기준을 임의로 정하지 마.
구현 중 핵심 결정·오류 해결 시 WORK_REVIEW.md를 과제 폴더에 짧게 갱신해줘.
현재 환경의 규정을 우선하고 원본 자료를 보존해줘. 제공 Codex 업데이트,
외부 AI·개인 키 연결, UI 자동 조작, 과제 자료 외부 전송·Git push는 하지 마.
```

저장소 다운로드가 실패해도 반복 설치에 시간을 소진하지 않습니다. 실패 원인을 한 번 확인하고, 허용된 대체 다운로드나 제공된 자료로 요구사항 분석을 계속합니다. 접근 제한을 우회하지 않습니다. 실제 모델과 effort는 선택 화면에서 설정하며, 프롬프트에 적었다는 이유로 전환됐다고 간주하지 않습니다.

## 3. 업무 담당자에게 질문

README에서 이미 답을 찾은 질문은 빼고, 구현 결과를 바꾸는 것부터 묻습니다.

| 질문의 목적 | 질문 예시 |
|---|---|
| 사용자와 핵심 업무 | 이 결과를 누가 어떤 업무 단계에서 사용하며, 가장 먼저 해결해야 하는 불편은 무엇인가요? |
| 필수 결과와 정확성 | 반드시 있어야 할 결과와 맞았다고 판단할 기준은 무엇인가요? 실제 입력 하나와 기대 결과를 알려주실 수 있나요? |
| 업무상 예외 | 자료가 충돌하거나 값이 빠졌을 때 따르는 우선순위와 처리 기준이 있나요? |

처음에는 가장 중요한 질문 2~3개로 시작하고, 답변에서 남은 쟁점을 좁혀 후속 질문합니다. UI 사용법·제출 절차는 환경 도우미에, 접속·실행 장애는 지정된 신고 창구에 문의합니다.

받은 답변을 요약하다 업무 기준을 바꾸지 않도록 가능한 한 원문으로 Codex에 전달합니다. README와 충돌하면 우선순위를 확인합니다. 확인 대기 중에는 그 답변에 의존하지 않는 파일 구조 파악·입력 검사 등을 진행할 수 있습니다.

중요한 미확인 사항이 없으면 질문을 억지로 만들지 않고 다음 단계로 넘어갑니다. 아래 요청의 답변 자리에는 “추가 질문 없음, README의 확정 사항 기준”이라고 적습니다.

## 4. 답변 반영 후 최소 구현

```text
담당자 답변은 다음과 같아: [답변 원문]
확정 사항과 미확인 사항을 구분하고 필수 요구사항 → 결과물 → 검증 방법을 연결해줘.
확정된 범위부터 실제 입력 하나를 끝까지 처리하는 최소 버전을 구현해줘.
계획은 짧게 하고 기존 구조를 활용해줘. 완료된 흐름은 실행해서 확인해줘.
업무상 핵심 기준이 미확정이면 그 부분만 보류하고 독립적으로 할 수 있는 작업을 진행해줘.
```

| 요구된 결과물 | 먼저 완성할 흐름 | 첫 확인 |
|---|---|---|
| 분석·집계 파일 | 파일 하나 → 정제·집계 → 지정 형식 저장 | 작은 표의 합계·분모·단위 직접 대조 |
| 보고서·업무 문서 | 근거 자료 → 핵심 결론·표 → 요구된 문서 | 수치·출처·요구된 항목과 생성 파일 확인 |
| 자동화·API·프로그램 | 실제 입력 → 핵심 처리 → 출력 | 정상 입력과 중요한 오류 입력 실행 |
| 화면·서비스 | 사용자 입력 → 실제 처리 → 화면 결과 | 사용자가 주요 동작을 직접 확인 |
| 기존 결과물 개선 | 오류나 불편 재현 → 최소 수정 | 같은 사례 재확인 및 관련 기능 확인 |

화면은 요구될 때 만듭니다. 홈페이지가 필요하면 디자인 방향 하나를 정하고 필수 기능이 연결되는 버전부터 구현합니다. 외부 계정·이미지 탐색·과도한 시안 비교를 기본 작업으로 추가하지 않습니다.

## 5. 실행 중 상태 판단

- **승인 대기:** 명령과 권한 범위를 읽고 응답합니다. 기다리기만 하면 진행되지 않습니다.
- **실행 중:** 동일한 요청을 반복해서 보내지 않습니다. 패키지 설치·빌드·서버 대기는 모델 속도 설정과 별개입니다.
- **오류:** 재현 단계·실제 오류·기대한 결과를 함께 전달합니다. 무작정 프로젝트 전체를 다시 만들지 않습니다.
- **서버 실행:** 환경에서 여러 터미널을 지원하면 Codex용과 서버용을 나눕니다. 서버가 계속 실행되는 것은 정상일 수 있으며 해당 터미널을 닫지 않습니다.
- **화면 검증:** 허용된 플랫폼 미리보기를 사용자가 직접 조작합니다. 포트·호스트 설정은 해당 환경 안내를 따릅니다. UI 자동 조작이 금지된 환경에서는 자동 브라우저 도구를 사용하지 않습니다.

## 6. 남은 필수 요구사항과 검증

최소 버전이 동작하면 아직 빠진 필수 항목과 중요한 예외를 채웁니다. 남은 시간이 줄면 선택 기능부터 줄이고 필수 결과·검증·제출 시간을 지킵니다.

```text
README와 담당자 답변을 기준으로 필수 요구사항별 충족 여부와 근거를 정리해줘.
verification-before-completion 지침을 읽고 결과물에 맞는 실제 검증을 해줘.
계산은 작은 사례로 대조하고, 프로그램은 정상·오류 입력과 실행 방법을 확인해줘.
실패한 항목은 수정 후 재검증해줘. 하지 못한 검사는 미확인으로 남겨줘.
```

다른 모델의 동의나 코드 존재만으로 통과 처리하지 않습니다. 변경이 없고 이미 통과한 검사를 이유 없이 반복하지 않습니다. 사용자가 직접 해야 하는 확인은 실제 수행 후 관찰 결과를 남깁니다.

## 7. 제출 전 정리와 본인 복습

- 지정된 파일명·경로·형식·실행 방법과 저장 상태를 확인합니다. 별도 지정이 없다면 제공 README를 훼손하지 않는 위치에 실행 안내를 둡니다.
- 실제 제출 대상에 필요한 결과가 있는지 확인합니다. 참고 레포를 과제 결과물로 오인하지 않습니다.
- `WORK_REVIEW.md`를 최종 파일·검증 기록에 맞춰 정리합니다. 제출 문서의 필수 여부와 파일명은 과제 안내를 따릅니다.
- **업무 문제 → 처리 흐름 → 선택 이유 → 문제 해결 → 검증 근거 → 한계**를 본인이 설명해 봅니다. 이해가 안 되는 부분은 AI가 허용된 단계가 끝나기 전에 질문합니다.
- 미완성·미검증·가정을 완료 사실처럼 바꾸지 않습니다. 개인정보·키·비공개 자료를 공개 저장소에 올리지 않습니다.

## 8. 제출 확정과 후속 단계

미리보기·파일 저장·최종 확정은 서로 다른 동작일 수 있습니다. 실제 화면에서 제출 대상·안내·확정 후 수정 가능 여부·전체 종료 시각을 먼저 확인한 뒤 확정합니다. 후속 단계가 남아 있으면 완료 확인까지 진행합니다.

AI가 금지된 후속 단계에서는 AI를 호출하거나 우회 도구를 사용하지 않습니다. 기록 파일 열람·복사·붙여넣기 허용 여부도 가정하지 않습니다. 본인이 실제로 한 일을 **결론 → 이유 → 작업 근거 → 한계** 순서로 직접 설명합니다. 질문의 전제가 구현과 다르면 차이를 밝히고, 하지 않은 작업을 했다고 쓰지 않습니다.
