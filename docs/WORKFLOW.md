# 스킬 설치 후 문제 해결 순서

[README](../README.md) · [사용 안내](USAGE.md) · [스킬 목록](CATALOG.md) · [모델 역할](MODELS.md)

스킬은 작업 방법을 안내합니다. 해결할 문제와 제출할 결과물은 과제의 README, 제공 자료, 담당자의 답변으로 정합니다. 화면·웹사이트가 필요한지도 이 단계에서 판단합니다.

## 전체 흐름

| 단계 | 할 일 | 다음 단계로 넘어갈 기준 |
|---|---|---|
| 1. 읽기 | README, 파일 목록, 실행 방법, 제출 조건 확인 | 필수 결과물과 모르는 점을 구분했다 |
| 2. 질문 | 실제 업무 흐름과 완료 기준 확인 | 중요한 모호함을 해결했다 |
| 3. 범위 확정 | 요구사항별 결과물·검증 방법 연결 | 무엇을 만들고 어떻게 확인할지 정했다 |
| 4. 최소 구현 | 실제 입력에서 결과까지 한 흐름 완성 | 작은 실제 사례가 끝까지 동작한다 |
| 5. 보완 | 남은 필수 요구사항과 예외 처리 | 필수 기능이 모두 연결됐다 |
| 6. 검증·수정 | 실제 실행, 계산 대조, 실패 항목 재검증 | 요구사항마다 확인 근거가 있다 |
| 7. 제출·설명 | 지정 형식으로 정리하고 실행 방법 확인 | 결과와 판단 근거를 직접 설명할 수 있다 |

## 1. README와 자료부터 읽기

과제 작업 폴더에서 Codex를 시작합니다. 처음에는 아래 내용만 정리하도록 요청합니다.

```text
README와 제공 파일 목록, 실행·제출 안내를 읽어줘.
사용자, 해결할 업무 문제, 입력 자료, 필수 결과물, 제약, 완료 기준을 표로 정리해줘.
확정된 사실과 미확인 사항을 구분하고, 담당자에게 물을 핵심 질문을 최대 5개 뽑아줘.
아직 파일을 수정하거나 구현하지 마.
```

확인할 항목:

- **결과물:** 보고서, 분석 파일, 자동화 도구, API, 화면 중 무엇이 필요한가?
- **입력:** 어떤 파일·데이터·API를 사용하며, 기준 문서는 무엇인가?
- **환경:** 제공 도구와 실행 방법, 사용 가능한 연결은 무엇인가?
- **완료:** 어떤 상태가 되면 요구사항을 충족하는가?
- **제출:** 파일 경로·형식·실행 명령 등 지정 조건이 있는가?

README에 이미 적힌 내용은 반복해서 묻지 않습니다. 자료가 많으면 파일별 목적, 기준 날짜, 핵심 필드, 필요한 작업을 간단한 표로 정리합니다.

## 2. 현업 담당자에게 업무 기준 묻기

구현 방향이나 정답을 대신 정해 달라는 질문보다 실제 업무에서 판단이 필요한 부분을 묻습니다.

| 우선순위 | 질문 예시 | 확인하려는 것 |
|---|---|---|
| 1 | 지금은 어떤 순서로 일하고, 어느 단계에서 가장 시간이 걸리나요? | 해결할 업무 병목 |
| 2 | 이 결과를 누가 보고 어떤 결정을 하나요? | 사용자와 결과의 용도 |
| 3 | 결과에 꼭 있어야 하는 항목과 맞았다고 판단하는 기준은 무엇인가요? | 필수 출력·완료 기준 |
| 4 | 자료가 충돌하거나 값이 빠졌을 때 따르는 기준이 있나요? | 우선순위·예외 처리 |
| 5 | 이번 범위에서 제외해도 되는 기능이 있나요? | 구현 범위 |

가능하면 실제 입력 하나와 그때 기대하는 결과를 요청합니다. 답변이 모호하면 결론을 임의로 정하지 말고 선택지를 좁혀 확인합니다.

예: “불량률을 수량으로 계산하나요, 행 개수로 계산하나요?”보다 “검사 수량 합계를 분모로 계산하는 것으로 이해했습니다. 재검사 수량도 포함하나요?”처럼 자료를 읽은 뒤 남은 쟁점을 묻습니다.

## 3. 답변을 전달하고 구현 범위 확정하기

담당자의 답변을 원문 그대로 전달하고, 아래 표를 먼저 만들게 합니다.

| 필수 요구사항 | 만들 결과물 | 확인 방법 |
|---|---|---|
| 원본 수량에 근거한 비율 산출 | 그룹별 집계 파일 | 작은 샘플을 직접 계산해 비교 |
| 누락 데이터 확인 | 누락 목록과 처리 내역 | 누락이 있는 입력으로 결과 확인 |
| 처리 결과 추적 | 원본 행과 결과의 연결 정보 | 결과 하나를 원본으로 역추적 |

위 표는 데이터 분석 업무의 **가상 예시**입니다. 실제 요구사항으로 바꿔 사용합니다.

```text
담당자 답변은 다음과 같아: [답변 원문]
README와 함께 반영해 확정 사항, 아직 필요한 가정, 필수 기능, 제외 범위를 정리해줘.
필수 요구사항 → 결과물 → 검증 방법을 연결해줘.
작업에 맞는 스킬 2~3개의 SKILL.md와 참조 파일을 읽고, 적용할 부분을 짧게 설명해줘.
실제 입력 하나를 끝까지 처리하는 가장 작은 구현부터 계획해줘.
```

답변과 README가 충돌하면 어느 쪽이 우선인지 확인합니다. 확인할 수 없는 사항은 가정으로 표시하고, 나중에 바꾸기 쉬운 위치에 둡니다.

### 필요한 스킬만 선택하기

| 작업 | 우선 검토할 스킬 |
|---|---|
| 요구사항이 모호함 | `write-spec` |
| CSV·표 등 데이터 분석 | `explore-data`, `validate-data` |
| 화면이 필수 결과물임 | `frontend-design` |
| 재현되는 오류가 있음 | `systematic-debugging` |
| 완료 여부를 보고함 | `verification-before-completion` |

스킬 이름을 언급하는 데서 끝내지 않고 해당 지침을 실제로 읽게 합니다. 외부 연결이나 자동화가 필요한 부분은 현재 환경에서 허용되고 지원되는지 확인합니다. 설치한 스킬을 모두 쓸 필요는 없습니다.

## 4. 실제 입력 하나로 최소 흐름 구현하기

처음부터 모든 기능을 병렬로 만들지 말고 **입력 → 핵심 처리 → 요구된 결과**를 한 번 연결합니다.

```text
확정한 범위로 구현을 시작해줘.
제공된 실제 입력 하나로 입력 → 핵심 처리 → 결과 출력까지 먼저 완성해줘.
기존 구조와 제공 API·파일 형식을 따르고 원본 자료는 보존해줘.
이 흐름을 실제 실행해 결과와 부족한 점을 보고해줘.
필수 기능을 위해 필요하지 않은 로그인·설정 화면·외부 서비스는 추가하지 마.
```

- 분석 과제라면 먼저 실제 파일 하나에서 필요한 집계가 나와야 합니다.
- 문서 과제라면 근거 자료와 연결되는 핵심 결론·표가 먼저 나와야 합니다.
- 앱 과제라면 핵심 입력과 결과를 실제로 연결하고 필요한 화면을 붙입니다.

제공된 API 호출이 실패하면 실패 상태를 드러냅니다. 임시 데이터를 사용할 때는 명확히 구분하고, 최종 확인 전에 실제 연결을 검증합니다.

## 5. 남은 필수 기능과 예외 보완하기

최소 흐름이 동작하면 요구사항 표에서 아직 충족하지 못한 항목을 순서대로 채웁니다. 오류가 생겼을 때는 증상과 재현 방법을 함께 전달합니다.

```text
[입력/작업]을 하면 [실제 결과]가 나와. 기대 결과는 [기대 결과]야.
같은 조건으로 재현하고 원인을 확인한 뒤 필요한 부분만 수정해줘.
수정 후 이 사례와 영향을 받는 관련 흐름을 다시 확인해줘.
```

빈 입력, 잘못된 형식, 누락값, 중복, 계산 기준, API 실패 등 **해당 업무에 실제로 중요한 경우**를 골라 처리합니다. 모든 예외를 망라하느라 필수 흐름을 미루지 않습니다.

## 6. 검증하고 실패한 항목 다시 확인하기

```text
verification-before-completion 지침을 읽고 완료 검증을 해줘.
README의 필수 요구사항별로 충족 여부와 실제 확인 근거를 표로 정리해줘.
정상 입력과 중요한 예외 입력을 실행하고, 계산은 작은 샘플로 별도 대조해줘.
실패한 항목은 수정 후 다시 확인하고, 실행하지 못한 검사는 미확인으로 남겨줘.
```

확인 근거는 “코드가 있어 보임”이 아니라 실행 결과·산출물·계산 대조여야 합니다. 다음 세 가지를 구분합니다.

1. **동작:** 지정 방법으로 실행할 수 있고 필요한 결과가 나온다.
2. **정확성:** 업무 기준과 실제 데이터에 맞는다.
3. **사용성:** 필요한 내용을 찾고 작업을 완료하기 쉽다.

화면이 있는 결과물은 사용자가 직접 주요 흐름을 확인합니다. 자동 검사가 통과해도 수량 기준을 잘못 이해했거나 필수 제출 파일이 빠졌을 수 있으므로, 마지막에는 README와 다시 대조합니다.

## 7. 제출 파일과 설명 정리하기

```text
지정된 제출 조건에 맞춰 결과물을 정리해줘.
실행 방법, 입력·출력 위치, 충족한 요구사항, 주요 판단 근거,
실제 검증 결과, 남은 한계를 짧게 작성해줘.
제출 경로와 필수 파일이 맞는지도 확인해줘.
```

작성한 설명을 직접 읽고 다음 질문에 자기 말로 답할 수 있는지 확인합니다.

- 어떤 업무 문제를 해결했는가?
- 담당자의 어떤 답변이 구현 방향을 바꿨는가?
- 이 방법과 계산 기준을 선택한 이유는 무엇인가?
- 정확성을 어떻게 확인했는가?
- 무엇이 미완성이며 더 개선한다면 무엇부터 할 것인가?

## 한 번에 보는 가상 예시: 검사 데이터 집계

**상황:** 담당자가 매일 검사 CSV를 수작업으로 합쳐 품목별 불량률을 보고한다. 과제는 반복 가능한 집계와 결과 파일을 요구한다.

| 단계 | 실행 예시 |
|---|---|
| 자료 읽기 | CSV의 품목·검사 수량·불량 수량·검사 구분을 조사한다 |
| 담당자 확인 | 재검사 포함 여부, 누락 처리, 필요한 집계 단위를 묻는다 |
| 기준 확정 | “최초 검사만 집계, 누락 행은 별도 표시, 품목별 집계”라는 답변을 반영한다 |
| 최소 구현 | 파일 하나를 읽어 품목별 검사·불량 수량과 비율을 CSV로 출력한다 |
| 확장 | 요구된 여러 파일 처리와 누락 목록을 추가한다 |
| 검증 | 검사 100개 중 불량 2개, 900개 중 불량 9개인 두 행의 합계가 1.1%인지 확인한다 |
| 제출 | 실행 방법, 결과 CSV, 누락 목록, 처리 기준과 검증 결과를 정리한다 |

두 행의 불량률 2%와 1%를 단순 평균하면 1.5%입니다. 수량 기준의 전체 불량률은 `(2 + 9) / (100 + 900) = 1.1%`입니다. **이런 업무 기준을 먼저 확정하는 것이 스킬을 많이 설치하는 것보다 중요합니다.**

## 시간과 모델 사용

- 전체 시간의 약 15%는 읽기·질문·범위 확정, 55%는 구현, 20%는 검증·수정, 10%는 제출 준비에 배분하는 것을 시작점으로 삼습니다. 실제 작업량과 마감에 맞춰 조정합니다.
- 기본 모델 하나로 맥락을 유지합니다. 작은 작업을 다른 모델에 맡긴다면 입력·기대 출력·제약·확인 방법을 함께 넘깁니다.
- 모델을 바꾸는 것보다 불명확한 요구사항과 잘못된 입력을 먼저 고칩니다.
- 마지막에는 새 기능을 추가하기보다 필수 요구사항, 재실행 가능 여부, 제출 파일을 확인합니다.
