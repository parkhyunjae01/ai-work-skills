# 모델을 업무 범위에 맞게 나누기

아래는 공식 공개 문서가 있는 네 모델의 **작업 배정 예시**다. 모델끼리 직접 비교한 성능 순위나 결과 품질 보장이 아니다. 실제 선택 가능 여부는 사용하는 제품·계정·조직 설정에 따라 확인해야 하며, 이 저장소를 설치한다고 모델 접근 권한이 생기지는 않는다.

## 모델별 역할 예시

| 모델·공식 문서 | 정확한 모델 ID | 맡기기 좋은 범위 | 넘길 때 정할 조건 |
|---|---|---|---|
| [Sol 6.1](https://developers.openai.com/api/docs/models/gpt-6.1-sol) | `gpt-6.1-sol` | 요구사항 파악·계획·핵심 구현·복잡한 오류·최종 통합 검토의 주 담당 | 목표·제약·수용 기준·실행 방법을 한 흐름으로 유지한다. |
| [Luna 6](https://developers.openai.com/api/docs/models/gpt-6-luna) | `gpt-6-luna` | 설계가 정해진 작은 함수·입력 검사·문구·스타일 수정 | 대상 파일·입출력·변경 범위·확인 방법을 명시한다. 범위가 커지면 주 담당에게 돌린다. |
| [Terra 5.6](https://developers.openai.com/api/docs/models/gpt-5.6-terra) | `gpt-5.6-terra` | 작은 일반 모듈·요구사항 대조·범위를 제한한 보조 검토 | 확인할 요구와 근거를 지정한다. 문서나 UX에 특화됐다는 전제로 배정하지 않는다. |
| [Sol 6.0](https://developers.openai.com/api/docs/models/gpt-6-sol) | `gpt-6-sol` | 대체 구현 담당 또는 기존 변경의 누락·회귀 검토 | 전체 재작성보다 재현 가능한 문제와 필요한 수정에 범위를 둔다. |

`Terra 5.6`과 `Terra 6.1`은 다른 모델이다. 표시 이름이 비슷하더라도 위 ID와 실제 선택 항목을 대조한다. 공식 모델 설명과 제공 조건은 링크의 현행 문서가 기준이다.

## 한 모델로 시작하고 필요한 부분만 나누기

기본 예시는 **Sol 6.1로 요구사항·핵심 구현 → 필요하면 Luna 6로 작은 수정 → Sol 6.1로 통합 검증**이다. Terra 5.6이나 Sol 6.0의 별도 검토는 선택 사항이다. 네 모델을 모두 사용하거나 동시에 실행할 필요는 없다.

분리할 일은 입력과 완료 조건이 분명해야 한다. 독립적인 검토·문구 수정·작은 테스트처럼 서로의 파일을 건드리지 않는 작업부터 나누면 통합 부담을 줄일 수 있다. 여러 모델을 썼다는 사실보다 변경 결과와 검증 근거가 중요하다.

| 넘길 정보 | 예시 |
|---|---|
| 목표 | 검색어가 비어 있을 때 조회 요청을 막기 |
| 작업 범위 | 지정한 입력 처리 함수와 관련 테스트 |
| 유지할 조건 | 기존 API와 화면 동작 유지, 새 패키지 추가 없음 |
| 완료 기준 | 빈 값·공백·정상 값의 실제 동작 확인 |
| 보고 내용 | 변경점·실행한 검사·남은 미확인 사항 |

## 설정과 검증

Codex CLI에서 제공된다면 `/status`와 `/model`로 현재 모델과 선택 항목을 확인한다. 다른 화면이나 제품에서는 해당 모델 선택 UI를 사용한다. 모델을 바꾸기 전에는 결정 사항·수정 파일·남은 작업을 짧게 남겨 맥락을 전달한다.

추론 강도는 문제의 모호함과 검증 난도에 맞춘다. 높은 설정이 시간·토큰을 더 사용할 수 있으므로 모든 작업에 최고 설정을 고정하지 않는다. 비용·지연·제공 범위는 변할 수 있어 이 문서에 고정 수치나 보장된 우열을 두지 않는다. [Codex 모델 안내](https://learn.chatgpt.com/docs/models?surface=cli)

최종 검토에서는 필수조건과 산출물을 대조하고, 실제 실행 결과를 확인한다. 검토자가 다른 모델이어도 같은 오해를 공유할 수 있다. 테스트·원자료 재계산·직접 확인으로 결과를 뒷받침한다.
